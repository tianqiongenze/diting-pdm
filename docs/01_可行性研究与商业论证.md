## 1. 商业论证（Business Case）

### 1.1 损失结构：为什么"计划停机"比"非计划停机"便宜 5–10 倍

原文给出的经验倍数，我们把它拆成可核算的科目：

| 成本科目 | 非计划停机 | 计划停机 | 差异来源 |
|---|---|---|---|
| 直接产值损失 | 全额（含在制品报废） | 部分（可提前备库存） | 排产可转移 |
| 备件成本 | 紧急采购溢价 30–200% | 常规采购 | 提前期 |
| 人工成本 | 加班/外委溢价 50–150% | 正常工时 | 排班 |
| 二次损伤 | 常见（轴承抱死伤轴） | 极少 | 故障扩大 |
| 交付违约 | 可能（罚金） | 可协商 | 客户沟通窗口 |
| 安全/环保 | 可能触发事件 | 可控 | 风险敞口 |

**结论：预测的价值不在"知道会坏"，在"把非计划变成计划"。** 这句话决定了系统设计：**输出必须是"窗口"，不是"分数"。**

### 1.2 ROI 模型（单厂、20 台关键设备，假设值需替换为实际）

| 参数 | 假设值 | 说明 |
|---|---|---|
| 关键设备数 | 20 台 | 首期范围 |
| 年非计划停机次数 | 24 次（1.2 次/台·年） | 行业中等水平 |
| 单次平均损失 | ¥ 18 万 | 含产值+备件+人工 |
| 年非计划停机损失 | ¥ 432 万 | — |
| 目标下降幅度 | 30% | 保守 |
| 年化收益 | **¥ 130 万** | 432 × 30% |
| 备件呆滞下降收益 | ¥ 25 万 | 按库存 500 万 × 5% |
| 人工效率收益（诊断工时） | ¥ 30 万 | 专家工时释放 |
| **年化总收益** | **¥ 185 万** | — |
| 一次性投入（软件+集成+硬件） | ¥ 120 万 | 不含产线改造 |
| 年运营成本（云/人力/维护） | ¥ 45 万 | — |
| 投资回收期 | **约 10.4 个月** | 120 / (185−45) |
| 3 年 NPV（折现 8%） | 约 ¥ 240 万 | — |

> ⚠️ 以上为**论证用假设**，P1 阶段必须用工厂真实台账替换。ROI 模型的可信度取决于"单次停机损失"这一个数字，必须让财务签字。

### 1.3 不做的代价（Do-Nothing Cost）

- 关键设备平均役龄 > 8 年，故障率进入浴盆曲线上升段
- 老师傅 3 年内退休，经验无沉淀 → 诊断能力断崖
- 备件靠"猜"备货，资金占用高且仍缺件

## 2. 技术可行性

### 2.1 五项关键技术成熟度评估（TRL）

| 技术 | TRL | 判断 | 依据 |
|---|---|---|---|
| 工业协议接入（OPC UA / Modbus / S7） | 9 | 成熟，直接采购/开源 | Neuron、supOS 等已覆盖 70+ 协议 |
| 振动特征与故障诊断（FFT/包络/阶次） | 9 | 成熟，标准完备 | ISO 20816 / GB/T 19873 系列 |
| 阈值与规则引擎 | 9 | 成熟 | — |
| 结构化数据基础模型（LimiX 类） | 6–7 | 可用但需验证，**有许可风险** | LimiX-2 权重非商用；初代 Apache 2.0 |
| LLM Agent 工具调用 + Harness 工程 | 7 | 可用于"建议生成"，**不可用于自动执行** | 2026 年 Harness 工程已形成 10 组件共识 |
| 多智能体会诊 | 5–6 | 架构可行，效果需 A/B 验证 | 学界与工业界均在探索期 |

**结论：技术可行性成立，但必须"以成熟技术为骨架、以新技术为增益"，不能让 TRL 5–6 的组件承担主链路。**

### 2.2 关键技术验证清单（P1 阶段必须做完，否则不许进 P2）

| # | 验证项 | 通过标准 | 方式 |
|---|---|---|---|
| T1 | 单台设备全链路打通 | 从传感器到报告 ≤ 5 分钟端到端 | 现场 |
| T2 | 时间戳一致性 | 全厂时钟偏差 ≤ 50 ms | NTP/PTP 核查 |
| T3 | 传感器校准状态 | 100% 有校准记录且在有效期内 | 台账核查 |
| T4 | 故障模式库覆盖 | 覆盖目标设备 Top 8 故障模式 | 专家评审 |
| T5 | LLM 工具调用准确率 | 意图识别 ≥ 95%，参数抽取 ≥ 90% | 100 条测试集 |
| T6 | 提示注入防护 | 恶意指令拦截率 100% | 红队测试 20 例 |
| T7 | 断网降级 | 断网 30 分钟，本地诊断不中断 | 混沌测试 |

## 3. 方案选型论证（Alternatives Analysis）

### 3.1 三条路线对比

| 维度 | A. 采购商用 PdM 套件 | B. 全自研 | C. 开源组装 + 自研决策层（**推荐**） |
|---|---|---|---|
| 上线速度 | 快（3 个月） | 慢（12 个月+） | 中（4–5 个月） |
| 单点成本 | 高（¥200–500 万/厂） | 中 | 低–中（¥100–150 万） |
| 数据主权 | 差（多为 SaaS） | 好 | 好（可全本地） |
| 决策层可定制 | 差（厂商模板） | 好 | **好（核心自研）** |
| 协议适配 | 好 | 差（重复造轮子） | **好（复用开源）** |
| 长期演进 | 受厂商路线约束 | 自主 | 自主 |
| 风险 | 供应商锁定、按点位收费 | 工期与人才风险 | 开源组件维护风险（可控） |

**推荐 C，且明确分工：**

```
┌─────────────────────────────────────────────┐
│  自研（护城河）                               │
│  · 决策会诊层（L4）                           │
│  · Agent Harness 运行时（权限/审计/评测）      │
│  · 故障模式知识库与判据                       │
│  · 方案卡与经济性模型                         │
├─────────────────────────────────────────────┤
│  复用开源（不重复造轮子）                      │
│  · 协议接入：Neuron / supOS CE               │
│  · 时序存储：TDengine                        │
│  · 消息：EMQX                                │
│  · 模型服务：LimiX（验证用）/ 时序模型         │
│  · 编排：K8s / K3s + ArgoCD                  │
├─────────────────────────────────────────────┤
│  采购（有商业支持才买）                        │
│  · 工业网关硬件                               │
│  · 加速度计/温度传感器（含校准服务）            │
│  · 私有化推理服务器（可选）                    │
└─────────────────────────────────────────────┘
```

### 3.2 为什么"决策层必须自研"

因为决策层要接的是**这家工厂的排产规则、备件编码、班组排班、成本口径**——这些没有通用产品。买了商用套件，最后还是要二次开发，且被框架绑死。

## 4. 组织可行性（本土化落地视角）

### 4.1 四类利益相关者与真实诉求（TOGAF 干系人地图）

| 干系人 | 表面诉求 | 真实诉求 | 应对策略 |
|---|---|---|---|
| 设备副总 | "上个 AI 系统" | 别在我任内出大事故 | 先做"看得见"的告警治理，快速出成绩 |
| 设备科长 | "减少故障" | 别给我增加填表工作量 | 方案卡自动带工单草稿，减少他的录入 |
| 维修班长 | "早点知道" | 别让我白跑一趟 | 误报率是生命线，宁漏勿滥（首期） |
| 一线操作工 | "别烦我" | 别让我判断技术问题 | 只推"需要你做的事"，不推分数 |
| IT/信息安全 | "别出事" | 合规免责 | 等保三级、审计留痕、数据不出厂 |
| 财务 | "别乱花钱" | 可核算的 ROI | 用他的口径算停机成本 |

**本土化关键判断：**
> 在中国工厂，**系统失败的第一原因不是算法不准，是"增加了基层工作量却没减少他的麻烦"**。
> 因此设计原则第 0 条：**任何新增流程，必须同时减少一个旧动作。**（例：生成工单草稿 = 减少手工填单）

### 4.2 变革管理三件事

1. **标杆设备先行**：选一台"大家都知道它老出问题"的设备，30 天内做出一次成功预警，用事实说话。
2. **老师傅入伙**：把 2 位老师傅聘为"判据评审专家"，给署名、给津贴，让他们成为系统的作者而非替代对象。
3. **周报机制**：每周一封"设备健康周报"，只写 3 件事：本周新增预警、本周验证结论、下周关注点。**不写技术指标。**

## 5. 法规与标准可行性

| 关注点 | 适用要求 | 结论 |
|---|---|---|
| 数据出境 | 数据留在厂内，不出境 | ✅ 无出境合规问题 |
| 生成式 AI 服务 | GB/T 45654-2025（2025-11-01 实施） | 需做语料安全、内容过滤、标注、审计 |
| 大模型能力 | GB/T 45288.1-2025 通用要求 | 作为模型选型与评测依据 |
| 网络安全 | GB/T 22239-2019 等保三级 | 需做定级备案、测评 |
| 工控安全 | IEC 62443-3-3（SR 要求） | 需做区域/管道划分 |
| 功能安全 | GB/T 20438 / IEC 61508 | 本系统**不参与安全联锁**，仅作建议，降低 SIL 要求 |
| 资产管理 | ISO 55000 / GB/T 33172 | 维护策略需与资产管理体系对齐 |
| AI 治理 | ISO/IEC 42001 | 建议按体系建，不急于认证 |

> **重要合规红线：本系统输出"建议"，不输出"指令"。** 任何与安全联锁（SIS）相关的动作，必须由人工在既有安全体系内执行。这一条写入架构约束（见 docs/03 §2）。

## 8. 阶段 A 架构愿景（TOGAF 交付物摘要）

**愿景陈述：**
> 让工厂里每一台关键设备，都能在"坏之前 14 天"给出一个**可执行、可核算、可追责**的维护方案，而不是一个分数。

**架构目标（3 条）：**
1. 诊断能力从"人"转移到"系统"，常规诊断 80% 不依赖专家。
2. 预警必须落到"窗口 + 备件 + 人"，转化率 ≥ 60%。
3. 断网可用、写操作留痕、结论可回放。

**架构原则（6 条，详见 docs/03 §2）：**
P1 建议不指令 · P2 证据可回放 · P3 降级优于崩溃 · P4 协议无关 · P5 人机共决 · P6 单点可替换
