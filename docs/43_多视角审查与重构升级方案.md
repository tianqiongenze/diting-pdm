## 一、招标师视角（采购与商业论证）— 5.3/10

### 优势
- **ROI 模型完整**：docs/14 §8 的三级摊薄（平台 ¥180 万 + 基地 ¥25 万/个）逻辑清晰，20 基地回收期 3.4 个月，是集团客户的核心商业逻辑
- **需求编号连续**：FR-901~913 / NFR-201~205 避开既有编号，RTM 可追溯
- **验收标准有量化**：跨基地一致性、判据 24h 生效、供应商越权 100% 失败

### 差距
| 问题 | 证据 | 影响 |
|---|---|---|
| **只落地了 1 个租户** | CronJob 硬编码 `X-Tenant-Id: site-a`（cronjob-ops.yaml:69,129,219）；dashboard.html 硬编码 `value="site-a"`（server.py:380） | 招标演示时无法展示跨基地对标，FR-905/NFR-201 全部无法验收 |
| **C1–C8 未回收** | docs/14 §1.2 明确"没有回收之前，任何工期承诺都是编的" | 但 C1（国内外分布）、C7（海外合规）直接决定部署架构 |
| **无量化 SLA** | 验收标准说"HI 口径一致"，但没说允许多大偏差 | 招标方无法据此验收 |
| **行业包未实现** | FR-910 要求 SPI 插件化，实际 `alert_rule` 是单租户表 | 迁移到汽车行业包（FR-912）无代码路径 |

### 风险
- **最大风险**：演示时只能展示 site-a 的 1200 台设备，评审专家问"20 个基地怎么管"时只能翻文档
- **建议**：至少做出 3 个租户的数据隔离演示（site-a/site-b/site-c），各 200 台

## 三、资深架构师视角（系统架构与技术选型）— 6.3/10

### 优势
| 项 | 证据 |
|---|---|
| Litestar + Granian 选型合理 | 比 FastAPI+uvicorn 吞吐更高，msgspec 原生集成 |
| TenantQueryBuilder 强制多租户 | repository.py:49-73，SQL 不含 tenant_id 即报错，结果逐行断言防泄漏 |
| Outbox 模式保证事件一致性 | integration.py:7.3KB |
| NetworkPolicy 默认拒绝 | pdm-prod.yaml:57-130 |
| HPA + PDB 保障可用性 | pdm-prod.yaml:265-295 |

### 差距
| 问题 | 证据 | 影响 |
|---|---|---|
| **API 无版本化策略** | server.py 所有端点都是 `/v1/xxx`，无语义版本机制 | 改契约只能改路径，无法渐进 |
| **无 Schema 迁移工具** | impl/db/tidb/001-005.sql 是手动 SQL 文件，无 Alembic | 加表要手工执行 SQL，无回滚 |
| **CronJob 租户硬编码** | 见 FDE 节 | 违反配置与代码分离原则 |
| **HPA 阈值偏低** | pdm-prod.yaml:295 `averageUtilization: 70`，批量诊断时 CPU 飙升会误扩 | 应改为基于自定义指标或提高到 75 |
| **Pulsar consumer 无水平扩展** | pulsar_consumer.py 单进程消费，20 基地数据量上来后成瓶颈 | 需消费组+分区 |
| **CI buf breaking 检查是空的** | ci.yml:54 `buf breaking ... || echo "no baseline"` | API 破坏性变更不会被拦住 |
| **前端单文件过大** | console.html 133KB + screen.html 31KB，ConfigMap 上限 1MB | 还能撑，但已占 16% |

### 风险
- **中风险**：无迁移工具意味着加表靠手工，多人协作时容易冲突
- **建议**：引入 Alembic 管理 TiDB schema；CronJob 改为 env 参数化

## 四、AI 教授级高工视角（算法与模型）— 5.0/10

### 优势
| 项 | 证据 |
|---|---|
| HI 计算完全可解释 | domain.py 规则驱动，每个维度有 evidence 字段 |
| RUL 有边界保护 | repository.py:estimate_rul，历史不足 3 点返回 NULL，斜率≤0 返回 NULL |
| 降级结果不缓存 | server.py:809 `cacheable=lambda r: not r["degraded"]` |
| 批量诊断共享核心 | `_run_single_diagnose` 单点与批量共用，避免行为漂移 |

### 差距
| 问题 | 证据 | 影响 |
|---|---|---|
| **模型版本是字符串常量** | domain.py `MODEL_VERSION = "0.1.0"`，无版本表 | 无法做 A/B 对比、无模型迭代记录 |
| **无模型训练管线** | 无训练脚本、无特征存储、无评测集 | 算法迭代只能靠改代码 |
| **RUL 只有线性外推** | 无指数/卡尔曼滤波等替代方案 | 非平稳劣化场景不准 |
| **无反馈闭环** | 预测了故障、做了保养，但没记录"预测 vs 实际" | 无法量化模型准确率 |
| **知识库手动录入** | knowledge_case 靠人工填 | 诊断结论无法自动沉淀 |
| **无漂移检测** | 无数据分布监控 | 工况变化后 HI 可能系统性偏移 |
| **LLM 集成未实现** | docs/14 提到 LiteLLM+Milvus，代码中无 | AI 会诊功能缺失 |

### 风险
- **中风险**：模型不可迭代是长期隐患——工厂工况变化后 HI 会漂移，但无检测机制
- **建议**：至少加一个 `model_version` 表 + 诊断结果自动写入知识库的钩子

## 九、关键教训（本轮审查发现）

1. **"设计完备"不等于"可交付"**：docs/14 画了完美的联邦架构，但代码只有 1 个租户——评审时被问"第 2 个基地怎么接"会卡住
2. **CronJob 硬编码是隐性技术债**：配置写死在 YAML 里，每接一个基地改 3 处，违反配置与代码分离
3. **判据无版本化 = 集团对标不可信**：FR-903 要求"同型号同判据"，但当前 `alert_rule` 无版本号，改了阈值不知道哪些基地还在用旧版
4. **AI 模型无版本 = 无法迭代**：`MODEL_VERSION` 是字符串常量，改了代码就丢了历史，无法对比新旧模型效果

> 以上教训已同步写入 docs/44（部署方案）与 docs/45（重构交付报告）。
