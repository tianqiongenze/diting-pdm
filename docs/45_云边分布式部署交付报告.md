## 一、核心决策：边缘用 SQLite 替代 TiDB（用户问题回应）

**问题**：边缘部署需要 Rust 采集器、本地 TiDB、K3s 等大量组件，边缘可以用 SQLite 内存数据库替代 TiDB 吗？

**回答：可以，且是架构上的正确选择。** 但有一个关键修正——**不用内存模式（:memory:），
用文件 + WAL 模式**：

| 模式 | 是否选用 | 理由 |
|---|---|---|
| `:memory:` 纯内存 | ❌ | Pod 重启数据全丢；点检任务/告警/台账经不起重启 |
| **文件 + WAL** | ✅ | 持久化到 PVC（5Gi），重启不丢；WAL 让读写并发接近内存性能 |
| 本地 TiDB | ❌ | 每副本 ≥2C4G，边缘 K3s 承担不起；三组件运维复杂度与边缘定位相悖 |

### 实现方式：方言转换层，仓库函数零改动

`repository.py` 新增 `PDM_DB_BACKEND` 后端开关，SQLite 路径由 `_translate()` 统一
转换 SQL 方言，**所有 60+ 仓库函数一行未改**：

| MySQL 方言 | SQLite 转换 | 备注 |
|---|---|---|
| `%s` 占位符 | `?` | 全量替换 |
| `INSERT IGNORE INTO` | `INSERT OR IGNORE INTO` | 幂等键去重（3 处） |
| `ON DUPLICATE KEY UPDATE x=VALUES(x)` | `ON CONFLICT(pk) DO UPDATE SET x=excluded.x` | 5 张表在 `_UPSERT_PK` 登记主键 |
| `NOW()` / `NOW() - INTERVAL 1 HOUR` | `datetime('now')` / `datetime('now','-1 hour')` | UTC 口径与 TiDB 一致 |
| `TIMESTAMPADD(HOUR, sla_hours, created_at)` | `datetime(created_at, '+' \|\| sla_hours \|\| ' hours')` | SLA 超时计算 |
| `` `反引号` `` | `"双引号"` | 标识符引用 |

三个必须踩平的坑（冒烟测试覆盖）：

1. **事务静默回滚**：sqlite3 默认隐式事务，连接关闭时未提交写入全部丢失。
   `isolation_level=None`（真 autocommit）对齐 pymysql `autocommit=True`；
   `commit()` 保留为空操作（pulsar_consumer 显式调 commit 的兼容）。
2. **datetime 类型还原**：注册 `PARSE_DECLTYPES` 转换器，DATETIME 列读回仍是
   datetime 对象——`list_plans` 的 `isinstance(due, datetime)` 判断和 days_left
   计算依赖这一点。
3. **Row → dict**：`sqlite3.Row` 不能直接 `dict()`，用 `cursor.description` zip 转换。

### 2.3 云边链路架构（已实现）

```
边缘 site-b（K3s + SQLite WAL）
  ├─ 本地闭环：采集快照 → batch-diagnose → alerts/sync → 本地看板
  ├─ 判据：本地 site 规则 →（空时回退）集团 group 规则
  └─ 每 10 分钟 edge-sync CronJob：
       ├─ POST /v1/sites/register          → site_registry（心跳）
       └─ POST /v1/sites/site-b/summary   → read_edge_summary（仅聚合指标 L4）
                ↓ 集团中心（K8s + TiDB）
           fleet 对标：GET /v1/stats/fleet（跨租户聚合，本轮实测
           site-a 1200 台 + site-b 1200 台正确汇总）
```

断网行为（FR-908）：集团不可达时 edge_sync 静默降级 exit 0，边缘
诊断/告警/看板完全自治；恢复后下一轮自动补报，无重复数据（覆盖式）。
