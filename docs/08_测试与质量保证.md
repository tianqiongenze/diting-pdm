## 1. 三层驱动关系（先说清概念，避免团队各说各话）

```
ATDD  验收测试驱动：从"业务要什么"出发，三方（业务/开发/测试）共同写验收标准
  │
  ├─► BDD  行为驱动：把验收标准写成 Gherkin（Given/When/Then），可执行
  │
  └─► TDD  测试驱动：开发在写实现前先写单元测试，红→绿→重构
```

| | ATDD | BDD | TDD |
|---|---|---|---|
| 粒度 | 特性/故事 | 场景 | 函数/类 |
| 谁写 | 业务+测试+开发 | 三方共同 | 开发 |
| 语言 | 业务语言 | Gherkin | 代码 |
| 频率 | 每特性 | 每场景 | 每次提交 |
| 本项目落点 | `specs/*/spec.md` 的验收标准 | `specs/*/*.feature` | `tests/unit/` |

**关键纪律：Gherkin 场景不是"测试脚本"，是"需求的可执行表达"。写不出场景的需求，说明需求没想清楚。**

### 2.1 测试金字塔（本项目配比）

```
        ╱╲          E2E / 场景测试        ~10%   慢、脆、但真实
       ╱  ╲         30–50 条
      ╱────╲
     ╱      ╲       集成 / 契约测试       ~20%   中速
```

## 3. TDD 实践规范

### 3.1 红-绿-重构（强制）

```
1. 写一个失败的测试（红）——必须先看到它失败，且失败原因是"功能未实现"而非"语法错"
2. 写最少的代码让它通过（绿）——不写"将来可能需要"的代码
3. 重构（保持绿）——消除重复、改善命名
4. 提交（每个循环 ≤ 15 分钟）
```

### 3.2 单元测试要求

| 项 | 要求 |
|---|---|
| 命名 | `test_<被测单元>_<场景>_<期望>`，如 `test_hi_calculation_single_dim_fatal_returns_zero` |
| 结构 | Arrange-Act-Assert 三段，空行分隔 |
| 断言 | 一个测试一个概念；避免 `assert x == 1 and y == 2` |
| 隔离 | 不碰网络/数据库/时间（用 fake/注入 Clock） |
| 覆盖 | 行 ≥ 80%，核心算法（特征/HI/RUL）≥ 90%，分支 ≥ 75% |
| 速度 | 单测全量 < 60 秒 |

### 3.3 核心算法测试样例（特征与 HI）

```python
# tests/unit/test_health_index.py
import pytest
from pdm.health import compute_hi

class TestHealthIndex:
    def test_all_dimensions_healthy_returns_100(self):
        hi = compute_hi(s_vib=0.0, s_imp=0.0, s_temp=0.0, s_curr=0.0, s_trend=0.0)
        assert hi.value == 100

    def test_single_dim_fatal_forces_zero(self):
        # 单维度致命 → 整体致命（短板效应）
        hi = compute_hi(s_vib=1.0, s_imp=0.0, s_temp=0.0, s_curr=0.0, s_trend=0.0)
        assert hi.value == 0
        assert hi.level == "red"

    def test_missing_dimension_renormalizes_weights(self):
        hi = compute_hi(s_vib=0.5, s_imp=None, s_temp=0.0, s_curr=0.0, s_trend=0.0)
        assert hi.degraded is True
        assert abs(sum(hi.weights.values()) - 1.0) < 1e-6

    def test_contributions_sum_matches_delta(self):
        hi = compute_hi(s_vib=0.62, s_imp=0.55, s_temp=0.1, s_curr=0.0, s_trend=0.4)
        total_delta = sum(c.delta for c in hi.contributions)
        assert abs((100 + total_delta) - hi.value) < 1e-6

    @pytest.mark.parametrize("s,expected_level", [
        (0.0, "green"), (0.25, "green"),
        (0.35, "yellow"), (0.5, "orange"), (0.7, "red"),
    ])
    def test_level_boundaries(self, s, expected_level):
        hi = compute_hi(s_vib=s, s_imp=0, s_temp=0, s_curr=0, s_trend=0)
        assert hi.level == expected_level
```

### 3.4 测试替身策略

| 依赖 | 替身 | 说明 |
|---|---|---|
| 时序库 | In-memory fake | 固定数据集，可断言查询 |
| LLM | Stub（录制回放） | 避免测试依赖模型不确定性 |
| EAM | Mock Server（WireMock） | 可注入 500/超时 |
| 时钟 | 注入 `Clock` 接口 | 时间相关逻辑可测 |
| 传感器 | 波形回放器 | 用真实故障波形驱动 |

> **LLM 测试原则：** 单元测试**不调真实模型**。用录制的"提示→响应"对做回归；真实模型只在"AI 行为测试层"跑，且用温度 0 + 固定版本。

## 4. BDD 实践规范

### 4.1 Gherkin 写作规则

| 规则 | 说明 |
|---|---|
| 一场景一行为 | 不要在一个 Scenario 里验证 3 件事 |
| Given 用业务语言 | "Given 3 号压缩机已连续运行 30 天" 而非 "Given 数据库有 1000 行" |
| Then 可观测 | 必须能被外部观察到（返回值、事件、UI） |
| 避免 UI 细节 | 不写"点击第 3 个按钮"，写"提交确认" |
| 数据用表格 | 多组数据用 `Scenario Outline` |
| 每条 FR 至少 1 场景 | 需求追踪的硬要求 |

### 4.2 核心场景（节选，完整见 `specs/*/*.feature`）

```gherkin

  我希望用一句话知道设备现在健不健康
  以便决定是否需要进一步分析

  场景: 单维度致命时健康指数归零
    假设 3 号压缩机的驱动端轴承振动速度有效值为 11.2 mm/s
    并且 该值处于 ISO 20816-3 的 D 区
    当 我查询该设备的健康指数
    那么 健康指数应为 0
    并且 健康等级应为 "红色"
    并且 结论中应包含证据 "ISO 20816-3 D区"

  场景大纲: 四级告警边界

    并且 响应时限应为 <sla> 小时

    例子:
      | hi | level  | sla |
      | 95 | 绿色   | 0   |
      | 80 | 绿色   | 0   |
      | 79 | 黄色   | 168 |
      | 60 | 黄色   | 168 |
      | 59 | 橙色   | 72  |
      | 40 | 橙色   | 72  |
      | 39 | 红色   | 4   |
```

```gherkin
功能: 维护决策会诊
```

### 4.3 BDD 执行架构

```
.feature 文件（业务可读）
      │
      ▼
step definitions（Python: pytest-bdd）
      │
      ▼
系统边界（API / MCP 客户端 / UI 驱动）
      │
      ▼
测试环境（Docker Compose：TDengine + PG + mock EAM + stub LLM）
```

**规则：** 场景只通过**外部接口**驱动系统，不直接调内部函数（否则就是伪装的单元测试）。

## 5. ATDD：验收标准前置

### 5.1 三方评审（Three Amigos）

每个特性开发前，业务（设备专家）、开发、测试三方 45 分钟会议，产出：

1. 这个特性**不做什么**（边界）
2. 3–5 条验收场景（Gherkin 草稿）
3. 需要的数据样本（真实波形/工单）
4. 无法自动化的部分（人工验收项）

**没有三方评审的特性，不允许进入开发。**

### 5.2 验收标准模板

```markdown
## 特性：XXX
### 业务价值
（一句话，含可量化收益）

### 验收标准
- [ ] AC-1: （Gherkin 场景链接）
- [ ] AC-2: ...
- [ ] AC-3: （人工验收：设备专家签字确认判据合理）

### 不做什么
- 不做 ...
- 不做 ...

### 数据依赖
- 需要 3 条真实故障波形（含拆检报告）
```

## 6. 模型评测（第 6 层，最容易糊弄也最不能糊弄）

### 6.1 评测数据集

| 集 | 内容 | 规模 | 用途 | 更新 |
|---|---|---|---|---|
| Golden Set | 已拆检确认的故障案例 | ≥ 60 | 验收、回归 | 季度 |
| Replay Set | 连续 3 个月全量 | 20 台 | 误报率 | 月度 |
| OOD Set | 工况越界 | ≥ 30 | 鲁棒性 | 半年 |
| Synthetic | 注入故障 | 不限 | 冷启动 | 按需 |

### 6.2 指标定义（必须写清公式，避免各说各话）

| 指标 | 定义 | 目标 |
|---|---|---|
| 召回率 Recall | TP / (TP + FN)，按故障模式分别算 | ≥ 90%（关键模式） |
| 误报率 FPR | FP / (FP + TN)，按"设备·周"统计 | ≤ 0.5 次/台·周 |
| 提前期 Lead Time | 首次橙色 → 实际失效的天数 | 中位数 ≥ 14 天 |
| RUL MAE | mean(\|pred − actual\|) / actual | ≤ 20% |
| 区间覆盖率 | 实际值落在 [P10,P90] 的比例 | 75%–85% |
| 校准误差 ECE | 置信度分箱后 \|acc − conf\| 加权和 | ≤ 0.08 |
| 降级正确率 | 数据不足时正确标记降级的比例 | ≥ 95% |

> **为什么要求区间覆盖率 75–85% 而不是 100%：** 100% 说明区间过宽（没有信息量）；低于 70% 说明区间不可信。80% 名义区间实际覆盖 75–85% 才算校准良好。

### 6.3 评测报告模板

```markdown
# 模型评测报告 v{版本}
## 1. 被测对象
模型 / 版本 / 数据集指纹 / 代码 commit

## 2. 总体指标
（表格：召回/误报/提前期/RUL MAE/ECE）

## 3. 分故障模式指标
（每种故障模式单独一行，标出最差的 3 个）

## 4. 失效案例分析
（至少 5 例，含波形截图与误判原因）

## 5. 与基线对比
（相对上一版本，哪些变好、哪些变差）

## 6. 结论与建议
（是否可上线 / 适用边界 / 需要补充的数据）
```

**硬性要求：报告必须包含"失效案例"，只有好指标的评测报告一律打回。**

## 7. 混沌与降级测试（第 4 层）

### 7.1 故障注入清单

| # | 注入 | 期望行为 | 验证点 |
|---|---|---|---|
| C1 | 断网 30 分钟 | 边缘继续诊断与告警 | 本地告警正常，恢复后补传 |
| C2 | 单通道拔除 | 降级 + 置信度下调 | 不输出"正常" |
| C3 | 时钟跳变 +5 分钟 | 检测并标记 | 不产生错误趋势 |
| C4 | 数据冻结（值不变） | 识别为 STALE | 不当作"稳定健康" |
| C5 | 波形丢包 20% | 质量分下降，仍可分析 | 置信度下降 |
| C6 | PLC 拒绝连接 | 重连退避，其他设备不受影响 | 隔离性 |
| C7 | LLM 服务超时 | 降级到模板报告 | 仍输出建议动作 |
| C8 | EAM 返回 500 | 重试 3 次 → 人工队列 | 不声称成功 |
| C9 | 磁盘写满 | 按优先级淘汰波形 | 结论不丢 |
| C10 | Kafka 堆积 100 万条 | 背压 + 告警 | 不 OOM |

## 9. 质量门禁（Quality Gates）

| Gate | 条件 | 阻断 |
|---|---|---|
| **G-提交** | 单测通过 + Lint 通过 + 覆盖率不下降 | 阻断合并 |
| **G-合并** | 单测 ≥ 80% + 契约测试通过 + SAST 无高危 | 阻断合并 |
| **G-构建** | 镜像扫描无高危 + SBOM 生成 | 阻断部署 |
| **G-集成** | BDD 场景 100% 通过 + 混沌 C1–C3 通过 | 阻断进准生产 |
| **G-发布** | 性能达标 + 模型评测达标 + 安全测试通过 | 阻断上线 |
| **G-灰度** | 灰度 7 天误报率达标 + 无 P1 事件 | 阻断全量 |

### 9.1 Definition of Done（DoD）

一个特性"完成"必须同时满足：

- [ ] 代码已合并主干
- [ ] 单元测试覆盖（含边界与异常）
- [ ] 对应 Gherkin 场景通过
- [ ] 契约测试通过（如有接口变更）
- [ ] 文档更新（接口文档/ADR/运维手册）
- [ ] 可观测性埋点（日志/指标/trace）
- [ ] 已在测试环境演示给业务方
- [ ] 无新增技术债（或有登记）
- [ ] 回滚方案明确

**"能跑"不是完成，"能回滚、能观测、能解释"才是完成。**

## 10. 缺陷分级与响应

| 级别 | 定义 | 响应 | 修复 |
|---|---|---|---|
| P0 | 数据错误导致误判停机 / 越权 / 数据外泄 | 15 分钟 | 4 小时 |
| P1 | 核心功能不可用（诊断不出结果） | 1 小时 | 24 小时 |
| P2 | 功能异常但有绕过方案 | 4 小时 | 3 天 |
| P3 | 体验/文案/非关键 | 1 天 | 下迭代 |

**P0 定义里"误判停机"排第一**——因为一次错误的"建议停机"造成的损失，可能超过系统全年收益。

## 11. 测试环境矩阵

| 环境 | 用途 | 数据 | 模型 | 设备 |
|---|---|---|---|---|
| dev | 开发自测 | 合成 | stub | 模拟器 |
| ci | 自动化 | 固定夹具 | stub | 无 |
| test | 集成/BDD | 脱敏真实（1 个月） | 真实（小模型） | 波形回放 |
| staging | 准生产/性能/混沌 | 脱敏真实（3 个月） | 真实（全量） | 1 台真实设备 |
| prod | 生产 | 真实 | 真实 | 全部 |

**staging 必须有 1 台真实设备。** 纯回放的测试环境，永远测不出"传感器松动"这类物理问题。
