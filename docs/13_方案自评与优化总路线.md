## 3. v1 的三大结构性缺陷（不是补丁，是换地基）

### 缺陷 A：假设了"单厂"，真实是"集团 × 20 基地 × 供应商"

v1 全部文档默认 `site` 唯一、数据同域、网络可靠、集中部署。
真实：20 个基地跨省/跨国，网络质量参差，节点要能独立生存；供应商要低门槛接入；集团要对标。
**这不是加字段，是换部署模型。**

### 缺陷 B：假设了"读多写少、读侧可用"，真实是"高频写、读侧要联邦分析"

v1 写路径和读路径共用一套 PG + TDengine，靠 SQL 查询。
真实：20 基地 × 数千设备 × 毫秒级波形，写侧是热点；集团级对标是扫描全历史的重查询。
**必须 CQRS + 事件驱动分离读写。**

### 缺陷 C：假设了"一套语言"，真实是"不同子系统有不同最优语言"

v1 表面 Python+Go，实际 agent/算法/平台全是 Python。
真实：协议解析与 DSP 要 Rust；图查询与遥测管线要 Go；企业集成（EAM/ERP）要 Java；AI/Agent 要 Python。
**必须语言职责矩阵 + 构建体系。**

## 4. 优化四条主线

```
主线 A（地基）  DDD + 事件驱动 + CQRS + GraphQL        → docs/15
主线 B（骨骼）  雅迪集团场景 + 多基地联邦 + 供应商协同  → docs/14
主线 C（肌肉）  多语言最优实现 + 构建发布体系          → docs/16
主线 D（神经）  真实基础设施适配（10.167.2.175/176）   → docs/16 §4
```

### 4.1 主线 A：DDD + 事件驱动 + CQRS + GraphQL

| 项 | v1 | v2 |
|---|---|---|
| 领域建模 | 按技术层分层 | **按限界上下文**（8 个上下文） |
| 交互 | 同步 REST | **事件优先（CloudEvents + Kafka/NATS）+ 同步为辅** |
| 读写 | 一套库 | **CQRS 分离**：写侧 TDengine/MinIO/Kafka，读侧 PG + CH/Doris 联邦分析 |
| 查询 | REST 分页 | **GraphQL BFF**（看板一次拉全）+ REST/MCP 并存 |
| 一致性 | 没说 | **最终一致 + 幂等 + Saga + 事件溯源证据链** |

### 4.2 主线 B：集团化场景

| 项 | 内容 |
|---|---|
| 组织模型 | 集团 → 基地（20）→ 车间 → 产线 → 工位；供应商作为外部租户 |
| 部署模型 | 总部中心集群 + 基地边缘自治 + 供应商轻量接入 |
| 数据模型 | 租户隔离（tenant_id + 行级权限 + Kafka topic 命名空间） |
| 合规模型 | 按国别数据分级（境内不出境 / 境外受 GDPR 等 / 特征值可出境） |
| 推广模型 | **1 台 → 1 基地 → 3 基地 → 集团** 四级放大路径 |

### 4.3 主线 C：多语言

| 语言 | 承担 | 理由 |
|---|---|---|
| **Rust** | 协议解析引擎、DSP 计算核、边缘采集、波形编解码 | 零成本抽象、无 GC、内存可控、适合 24×7 工业边缘 |
| **Go** | Kafka/NATS 消费管线、GraphQL 网关、遥测、告警路由、审计链 | 高并发 I/O、部署简单、K8s 生态原生 |
| **Java** | 企业集成（SAP/Oracle/用友/金蝶/EAM）、多租户管理、规则引擎、BPM | 企业中间件生态、连接器丰富、运维体系成熟 |
| **Python** | ML/诊断/预后、Agent Harness、MCP 服务、报告渲染 | AI 生态唯一选择 |

**铁律：语言按"部署边界"划分，不按"目录"划分。** 每种语言一个独立构建单元 + 独立容器镜像 + 独立发布线。

### 4.4 主线 D：基础设施适配（已实测）

```
探测结果（2026-10-21）：
  10.167.2.175:6443  →  v1.28.2   可达
  10.167.2.176:6443  →  v1.28.2   可达    → 双控制面 HA 形态
  匿名用户：/version 可读，其它资源 403 → 需要凭据才能完成存量盘点
```

**下一步需要你提供**（见 docs/16 §9）：

2. 现有命名空间与服务清单（或授权我执行盘点命令）
3. 两台的资源配额与网络策略（NetworkPolicy 是否强制）
