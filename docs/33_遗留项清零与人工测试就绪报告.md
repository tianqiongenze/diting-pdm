## 二、网络问题：真正的根因是 Egress 策略

### 2.1 排查过程（含两次误判，如实记录）

| 步骤 | 观察 | 判断 | 是否正确 |
|---|---|---|---|
| ① | `master → Pod IP` 不通，`Pod → 同 ns Pod` 也不通 | 疑似 CNI 故障 | 方向对 |
| ② | 发现 178 条 iptables DNAT 规则显示 `--to-destination` 为空 | 判定 kube-proxy 规则损坏 | **❌ 误判** |
| ③ | 重启 worker1 kube-proxy 后仍 177 条 | 怀疑数据源损坏 | **❌ 继续误判** |
| ④ | 查 ingress-nginx 的规则**也是空参数，但 ingress 实际能用** | 意识到是 `iptables-save` 1.4.21 的**显示 bug** | ✅ 推翻前判 |
| ⑤ | 临时删除 `default-deny-ingress`，仍不通 | 排除 ingress 方向策略 | ✅ 缩小范围 |
| ⑥ | 逐条读 NetworkPolicy 定义 | 发现 `allow-egress-backends` 是 **Egress** 策略 | ✅ 命中 |

### 2.2 根因

`allow-egress-backends` 定义了 pdm-prod 的出向白名单：

```yaml
policyTypes: [Egress]
egress:
- to: [namespaceSelector: infra]          # 只允许到 infra
- to: [namespaceSelector: ai-platform]    # 只允许到 ai-platform
- to: [kube-system], ports: [53]          # 只允许 DNS
```

**没有「同命名空间」这一条**。一旦某个命名空间存在 Egress 策略，该空间所有 Pod 的
出向就被收窄为白名单——于是：

- Pod → infra（TiDB）✅ 通（在白名单）
- Pod → 同 ns 的 java-asset ❌ **被拦**
- Pod → 自己 Service 的 ClusterIP ❌ **DNAT 后仍落到同 ns Pod，被拦**
- 宿主机 → Pod ✅ 通（不受 Pod 出向限制）
- ingress → Pod ✅ 通（走 Ingress 方向策略）

这个组合极其迷惑：**看板、ingress 全部正常，只有服务间调用失败**。

### 2.3 修复

给 `allow-egress-backends` 增加一条：

```yaml
- to:
  - podSelector: {}     # 同命名空间任意 Pod
```

顺带修了第二个问题：`allow-from-ingress-controller` 的 `ports` 只列了 **8000**，
导致新加的 java-asset（8081）经 ingress 访问时 `upstream timed out`。
补上 8081。

### 2.4 验证

```
java-asset PodIP      OPEN
java-asset ClusterIP  OPEN
自身 ClusterIP        OPEN
infra TiDB            OPEN
```

## 三、看板部署自动化

### 3.1 问题本质

看板走 ConfigMap 挂载（`/app/static/dashboard.html`），**不经镜像构建**。
"改了仓库文件"和"线上生效"之间没有任何自动化保障——这是 docs/31 缺陷 2 的土壤。

### 3.2 方案

`impl/tools/deploy_dashboard.sh`，三个动作：

| 命令 | 作用 |
|---|---|
| `verify` | 只校验：比对仓库文件与 ConfigMap 内容的 SHA256 |
| `deploy` | 上传 → 更新 ConfigMap → 轮询 Pod 内文件 → 校验 HTTP 响应体 |
| `deploy --force` | 跳过预检直接部署 |

两个实现细节值得记：

1. **jsonpath 里 key 的点号必须转义**：`{.data.dashboard.html}` 会返回空，
   必须写 `{.data.dashboard\.html}`。第一次校验时报"不一致"就是这个原因。
2. **内容含 CRLF，必须落盘算哈希**，不能靠管道拼接。

### 3.3 纳入自动化测试

`browser_e2e.py` 新增 A6 组：

- A6.1 线上看板含最新功能（`function diag` / `function trend` / `id="trend"` / `confirmCard`）
- A6.2 本地文件非空并打印 SHA

这样每次跑浏览器测试都会顺带发现"代码新、线上旧"。

## 四、方案卡去重

### 4.1 策略

`save_recommendation_card` 增加去重窗口（默认 30 分钟，`PDM_CARD_DEDUP_MINUTES` 可调）：
同租户 + 同设备 + 同 verdict 在窗口内已有卡时**复用**，不新建。设 0 关闭。

选应用层去重而不是数据库唯一约束，是因为约束会抛错需要调用方处理，
而这里语义上就是"幂等查询"，返回已有结果更自然。

### 4.2 数据清理

`impl/tools/cleanup_cards.py`（默认 dry-run）：

```
总卡片数: 32
重复组: site-a/AGV-00006 MONITOR 17 张 | site-a/FAN-00004 ACT_NOW 15 张
已删除 30 张卡片、21 条确认记录 → 剩余 2 张
```

### 4.3 连带修掉的两个 bug

**① EAM 重复建单**：原代码先入队 EAM、后落库。去重复用旧卡时，
新建的 card_id 与旧卡不同，绕过了 `card:{id}` 幂等键 → 同一张卡重复建工单。
修复：**先落库拿到 effective_id，再入队**，且去重命中时跳过入队。

**② 去重后状态显示错误**：复用旧卡时只改写了 `card_id`，
`human_confirm.status` 仍是新建卡时的 `PENDING`，而库里实际是 `CONFIRMED`。
表现：前端显示"待确认"，点确认却收到 409。
修复：复用旧卡时从库中回填 `status` 与 `confirmed_roles`（后者查 `card_confirmation`）。

验证：

```

#2 card_id=REC-20261023-B04161 dedup=True
#3 card_id=REC-20261023-B04161 dedup=True
唯一 card_id 数: 1
status=CONFIRMED  confirmed_roles=['maintenance_supervisor','equipment_manager']
```

## 五、局域网访问：改用 nip.io，不改 Ingress

原计划给 Ingress 加 `host: 10.167.2.175` 规则，被 K8s 拒绝：

```
Invalid value: "10.167.2.175": must be a DNS name, not an IP address
```

改走 `nip.io`：这是公共 DNS 服务，把 `pdm-api.10.167.2.175.nip.io` 解析到
`10.167.2.175`。实测本机解析正常、ping 通，**人工测试零配置**。

同时给 java-asset 补了 Ingress（`/pdm-asset`），使资产 API 也能从局域网访问，
不再依赖 ssh 隧道。

## 九、仍需注意

1. **单副本风险**：python-diagnosis 现为 1 副本，节点故障即服务中断。
   根因是 worker1 CPU 配额打满（与 TiDB Operator 迁移受阻同源）。
   要恢复 2 副本，需加节点或腾挪负载。
2. **Egress 策略仍是白名单模式**：新增命名空间间调用时，记得同步加白名单，
   否则会重现"看板正常、服务间调用失败"的迷惑现象。
3. **kube-proxy 规则显示异常**：`iptables-save` 在 1.4.21 上对 DNAT 参数显示不全，
   排查网络问题时不要据此下结论，应以实际连通性测试为准。
