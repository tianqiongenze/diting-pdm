## 1. 问题定义（重新表述）

原文的洞察是对的，但表述还不够"可工程化"。我们把它翻译成三条可测量的差距：

| 现状 | 差距 | 可测量表达 |
|---|---|---|
| 工厂能测到振动/温度，但看不懂 | **诊断能力集中在 1–2 个人身上** | 关键设备诊断覆盖率 < 20%，专家离职即归零 |
| 能预测"某轴承 30 天后劣化" | **预测结果无法进入排产/备件/人力系统** | 预警→工单转化率 < 15% |
| 报警很多 | **没有分级路由与升级机制** | 无效告警占比 > 70%，夜班响应超时率 > 50% |

**结论：本项目交付的不是"预测模型"，是"从信号到工单的决策管道"。**

---

## 2. 范围边界（明确不做什么）

### 2.1 做（In Scope）

- 单厂区、关键旋转设备（电机 / 风机 / 泵 / 减速机 / 压缩机）的状态监测与诊断
- 振动、温度、电流、转速、油液（可选）多源数据接入与统一命名空间建模
- ISO 13374 六功能块的完整实现：DA / DM / SD / HA / PA / AG
- 自然语言诊断入口（MCP 工具化）
- 多角色会诊 → 输出**带排期与备件的维护方案卡**
- 边缘降级运行（断网可用）
- 全链路审计与回放

### 2.2 不做（Out of Scope，首期）

- ❌ 不做 DCS/PLC 的闭环控制（**永不自动下发控制指令**）
- ❌ 不做自动采购下单（只出建议，人工确认）
- ❌ 不做全厂设备一次性接入（首期 ≤ 20 台关键设备）
- ❌ 不做工艺质量预测、能耗优化（另立项）
- ❌ 不做设备设计改进/寿命再设计

> 边界写死在文档里，是为了防止项目在第 8 周变成"什么都能干"的泥潭。

## 3. 五层能力 × ISO 13374 六功能块（核心映射）

这是本方案与原文最大的结构性差异：**原文的五层是"技术栈分层"，ISO 13374 的六块是"信息处理职能"。两者必须正交映射，才能做到"每一层都有标准可依、每一个输出都有责任主体"。**

```
ISO 13374 职能      本项目能力层              交付物
─────────────────────────────────────────────────────────────
DA 数据采集    →   L1 数据底座        →   统一命名空间 + 时序库
DM 数据处理    →   L1 数据底座        →   清洗/对齐/重采样/质量分
SD 状态检测    →   L2 诊断大脑        →   特征 + 阈值 + 异常分数
HA 健康评估    →   L2 诊断大脑        →   健康指数 HI (0–100) + 四级色
PA 预后评估    →   L2 诊断大脑        →   RUL 分布（P10/P50/P90）
AG 建议生成    →   L3 交互入口        →   自然语言诊断报告
               →   L4 决策闭环        →   维护方案卡（排期/备件/成本）
─────────────────────────────────────────────────────────────
部署形态       →   L5 边缘落地        →   云边协同拓扑
```

**工程含义：**
- SD/HA/PA 三块的算法可以替换（LimiX / 时序模型 / 经典特征），但**接口契约不变**。
- AG 块被拆成两级：L3 面向"人"（解释），L4 面向"系统"（执行）。这是原文没区分的关键——**同一个"建议"，给人看和给 EAM 看，格式与约束完全不同。**

## 4. 目标架构一句话

> **一个以"设备"为中心的统一命名空间 + 一条以"证据链"为核心的诊断管道 + 一个受约束的 Agent Harness 运行时 + 一个带经济性计算的决策会诊层。**

四个关键词：

| 关键词 | 含义 | 反模式（我们要避免的） |
|---|---|---|
| 统一命名空间 | 设备/部件/测点/故障模式四类实体统一 ID，上层不问协议 | 每接一台设备写一套适配 |
| 证据链 | 每个结论都能回放到原始波形 + 特征 + 规则 + 模型版本 | "AI 说它快坏了" |
| 受约束 Harness | 工具白名单、写操作必确认、Stop Hook 防假完成 | 全自动 Agent 乱建工单 |
| 经济性计算 | 停机成本 vs 备件成本 vs 延期风险，量化到元 | 只给"建议更换" |

## 5. 关键指标（KPI 基线，待 P1 校准）

### 5.1 技术指标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 故障召回率（关键故障模式） | ≥ 90% | 黄金数据集回放 |
| 误报率（周均无效告警/设备） | ≤ 0.5 | 现场统计，连续 2 周 |
| 预警提前期（轴承类） | ≥ 14 天 | 从首次橙色到实际失效 |
| RUL 预测 MAE | ≤ 20% 实际剩余寿命 | 留出集 |
| 诊断时延 P95 | ≤ 8 s | 从提问到报告 |
| 数据完整率 | ≥ 99.5% | 采集点数/应采点数 |
| 断网降级可用性 | 100%（本地诊断不中断） | 混沌测试 |

### 5.2 业务指标

| 指标 | 目标 | 备注 |
|---|---|---|
| 预警→工单转化率 | ≥ 60% | 原文痛点的直接度量 |
| 非计划停机时长 | 下降 ≥ 30% | 同比 |
| 备件呆滞率 | 下降 ≥ 15% | 按建议窗口备货 |
| MTTR | 下降 ≥ 20% | 方案卡带步骤 |
| 专家依赖度 | 单点依赖从 2 人降到"系统可覆盖 80% 常规诊断" | 技能沉淀数 |

### 5.3 过程指标（工程侧）

| 指标 | 目标 |
|---|---|
| 需求→验收用例覆盖率 | 100%（每条 FR 至少 1 条 Gherkin） |
| 单元测试行覆盖率 | ≥ 80%（核心诊断算法 ≥ 90%） |
| 变更失败率 | ≤ 15% |
| 部署频率 | 周级（边缘月级） |

## 6. 团队与角色（RACI 见 docs/10）

| 角色 | 人数 | 关键职责 |
|---|---|---|
| 架构师（总体/Agent） | 1 | 架构决策、ADR、技术风险 |
| 数据/信号算法工程师 | 2 | DA/DM/SD/HA/PA 算法与评测 |
| 平台后端工程师 | 2 | 数据底座、MCP 服务、集成 |
| 前端/可视化 | 1 | 诊断报告、方案卡、看板 |
| 测试/质量 | 1（兼） | TDD/BDD、混沌、验收 |
| 领域专家（设备/可靠性） | 2（兼） | 故障模式库、标注、验收签字 |
| 运维/SRE | 1（兼） | 部署、监控、值班 |

**关键约束：领域专家必须"在位"且"签字"。** 没有设备专家签字的故障模式库，算法团队做出来的东西一定是自嗨。

## 7. 主要风险（Top 8，详见 docs/01 §7）

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | 传感器未校准 / 时间戳不统一 | 🔴 高 | G1 Gate 强制校验，不通过不进入 P2 |
| R2 | LimiX-2 权重非商用许可 | 🔴 高 | 商用前替换或采购授权；基线用经典特征模型 |
| R3 | 大模型幻觉生成不存在的故障模式 | 🔴 高 | 故障模式库白名单 + 引用强制 + Evaluator 独立校验 |
| R4 | 告警疲劳导致系统被弃用 | 🟠 中高 | 分级路由 + 抑制窗口 + 周报复盘 |
| R5 | 与 EAM/CMMS 集成受阻 | 🟠 中高 | 首期只做单向（读设备台账、写工单草稿） |
| R6 | 边缘框架（OpenClaw 类）高频变更 | 🟠 中 | 仅 POC，生产用自研稳定层 |
| R7 | 数据不出厂与模型效果冲突 | 🟠 中 | 特征值出厂 + 联邦式更新（后期） |
| R8 | 责任边界不清（AI 说错了谁负责） | 🔴 高 | 人工确认留痕 + 审计链 + 责任矩阵 |

## 9. 术语表（节选）

| 术语 | 含义 |
|---|---|
| DA/DM/SD/HA/PA/AG | ISO 13374 六功能块：采集/处理/状态检测/健康评估/预后评估/建议生成 |
| HI | Health Index，健康指数 0–100 |
| RUL | Remaining Useful Life，剩余使用寿命 |
| Harness | 智能体运行时工程（Agent = Model + Harness），非 CI/CD 平台 |
| MCP | Model Context Protocol，模型上下文协议，工具接入标准 |
| SDD | Spec-Driven Development，规范驱动开发 |
| EARS | Easy Approach to Requirements Syntax，需求句式规范 |
| ADR | Architecture Decision Record，架构决策记录 |
| 方案卡 | 本项目对"维护建议"的交付格式，含排期/备件/成本/风险 |
