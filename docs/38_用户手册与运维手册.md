## 2. 十六个视图怎么用

### 2.1 运营看板（默认首页）

**看什么**：全厂健康态势一眼掌握。

- 顶部 6 个 KPI：在监设备数、红/橙/黄/绿各级数量、方案卡数
- 健康趋势：默认展示第一台有健康度的设备，可输入位号查询
- 重点设备表：**默认只显示有健康度的设备**（勾掉复选框看全部）
- 关键度构成 + 最近事件：底部两块

**怎么操作**：点表格行「诊断」直接跳到诊断台；点「趋势」切换曲线。

### 2.2 告警中心 ⭐ 新增

**看什么**：需要处理的告警，按 SLA 紧急度排序。

- 5 个 KPI：红色告警、待处置、已确认、已升级、SLA 超时
- 列表每行：等级徽章、告警内容 + 处置建议、设备、规则、**SLA 剩余时间**、状态、负责人

**怎么操作**：

| 动作 | 说明 |
|---|---|
| **同步告警** | 从当前健康状态生成告警。**可重复点，不会重复建单** |
| **确认** | 认领告警，状态转「已确认」 |
| **升级** | 需上级介入时用，状态转「已升级」 |
| 筛选 | 按状态（待处置/已确认/已升级/已关闭）+ 等级（红/橙） |

> SLA 剩余时间为负会显示「超时 X.Xh」并标红。左侧导航告警图标出现红点表示有待处置。

### 2.3 设备台账

**看什么**：2400 台设备的完整清单。

**怎么操作**：
- 搜索框支持位号/名称模糊匹配
- 关键度（A/B/C）与等级（红/橙/黄/绿）两组筛选可叠加
- **点任意一行进入「设备 360」**

### 2.4 设备 360 ⭐ 新增

**看什么**：单台设备的全部档案。

| 区块 | 内容 |
|---|---|
| 顶部 | 位号、名称、类别、关键度、HI、等级、振动 RMS、测点数 |
| 健康趋势 | 近 7 天 HI 曲线 |
| 测点清单 | 全部测点（编号/量/方向/采样率） |
| 历史诊断 | 该设备所有诊断记录（时间/HI/等级/主因/模型版本） |
| 关联工单 | 该设备的方案卡及状态 |

**怎么操作**：右上「诊断」直接跳诊断台并自动执行。

### 2.5 组织产线 ⭐ 新增

**看什么**：按车间 → 产线 → 工位的层级看设备分布。

- 树形缩进显示层级
- 每行：设备数（**含子树汇总**）、红/橙/黄/绿/未评估数量
- 点「看设备」跳转到台账

> 当前 `asset.node_id` 只挂到车间级，所以产线层设备数为 0 属正常。

### 2.6 诊断工作台

**怎么操作**：输入位号 → 点「开始诊断」（进入页面会自动诊断默认设备）。

**看什么**：HI 大字 + 等级、维度分解条、五维雷达图、证据链（指标名/读数/偏离度/依据）。

### 2.7 诊断历史 ⭐ 新增

**看什么**：720 条历史诊断记录，按时间倒序。

**怎么操作**：搜索框按位号前缀过滤（如输入 `FAN` 筛出所有 FAN 系列）；可切换 50/100/200 条。

### 2.8 成本效益 ⭐ 新增

**看什么**：维护决策的投入产出。

| 指标 | 含义 |
|---|---|
| 净收益 | 避免损失 − 总成本 |
| 避免损失 | 若不维护导致的停机损失折算 |
| 总成本 | 停机 + 人工 + 备件 |
| ROI | 净收益 / 总成本 |

- 环形图：成本三项构成（**只统计主方案**，与总成本口径一致）
- 设备净收益 Top：哪台设备的维护最划算
- 方案对比：A-计划窗口 vs B-紧急调拨 的成本与停机时长

> 页面标注样本数（当前 4 张卡），样本少时结论仅供参考。

### 2.9 工单看板

**看什么**：方案卡三栏 Kanban（待确认 / 已确认 / 需立即处置）。

**怎么操作**：点卡片「确认」走多角色确认流程，全部角色齐备后移入「已确认」。

### 2.10 系统运维 ⭐ 新增

**看什么**：平台自身状态。

- 4 个 KPI：服务状态、事件投递数、投递失败数、集成 Outbox
- 核心表规模：12 张表行数，**大表带 `≈` 表示估算值**（如 feature_point 1 亿行）
- 服务与事件：healthz / 版本 / 传输 / 失败次数 / 最后错误
- 集成与缓存：Outbox 状态 / 缓存键数 / L2 是否启用

**怎么操作**：顶部「刷新」重新拉取。

# 第二部分 · 运维手册

### 2.11 点检巡检 ⭐ 本轮新增

按保养计划到期生成的点检任务。列表按「逾期 → 待执行 → 已完成」排序。

| 列 | 含义 |
|---|---|
| 任务号 | `INS-YYYYMMDD-XXXXXX` |
| 点检内容 | 计划名 + 检查项数量 |
| 剩余 | 距到期小时数；逾期显示红色「逾期 Nh」 |
| 结果 | 已完成任务显示「全部正常」或「N 项异常」 |

**执行点检**：点行尾「执行」→ 弹窗逐项填读数、选「正常/异常」→ 提交。

- 有任一「异常」时提示「建议开异常工单」
- 提交后该任务变「已完成」，并**自动把保养计划的下次到期推进一个周期**
- 同一个任务不能重复提交（第二次返回「task already done」）

**生成任务**：右上「按计划生成任务」按未来 3 天到期计划生成，默认上限 60 条。
需 `plan.edit` 权限（值班员点击会被拦）。

### 2.12 保养计划 ⭐ 本轮新增

1200 条计划，按设备关键度分级设周期：

| 关键度 | 周期 |
|---|---|
| A 类 | 7 天 |
| B 类 | 14 天 |
| C 类 | 30 天 |

- 「已逾期」筛选看需重新排程的计划
- 「7 天内到期」用于安排本周工作量
- 点行尾「设备」跳设备 360

> **口径提醒**：KPI「计划总数」取汇总接口的真实值（1200），
> 「当前展示 N 条」才是列表上限（300，按到期排序）。两者不同不是 bug。

### 2.13 备件管理 ⭐ 新增

库存按"单价 × 库存"计金额，低于安全库存的行标红并计入「低库存」KPI。

- 「领用 1」：扣减 1 件并生成领用记录（需 `card.confirm`）
- 「入库 10」：增加 10 件并生成入库记录（需 `plan.edit`）
- 库存不允许为负：超领会被拒绝并提示当前库存

### 2.14 知识库 ⭐ 新增

故障处置经验沉淀。可按**标题 / 根因 / 标签 / 设备号**检索，
`来源` 区分「诊断沉淀」与「人工录入」。点「新增案例」录入经验。

### 2.15 工单执行 ⭐ 新增

方案卡确认后的执行跟踪：**派工 → 开始执行 → 执行完成 → 验收 → 关闭**。

填方案卡号 + 动作 + 可选实际成本 + 备注即可记录，下方流水按时间倒序展示。
「已关闭」计数即闭环完成的工单数。

### 2.16 告警规则 ⭐ 新增

告警阈值不再硬编码。可改**阈值 / 等级 / SLA**，保存后下一轮告警同步即生效
（`alert-sync` 每 10 分钟跑一次）。修改需 `plan.approve` 权限（设备主管）。

### 2.17 登录、角色与主题 ⭐ 本轮新增

**登录**：右上「登录」→ 输入账号密码。登录后按钮显示「姓名 · 角色」，再点即登出。

| 账号 | 角色 | 能做 |
|---|---|---|
| `admin` / `Admin@2026` | 设备主管 | 全部，含查用户 |
| `sup_wang` / `Super@2026` | 维修主管 | 告警确认/升级、确认工单、编辑计划、执行点检 |
| `op_li` / `Oper@2026` | 值班员 | 查看、告警确认、执行点检 |

未登录时页面可用（后端兼容模式），但写操作会提示"需登录/无权限"。
上线前把 `PDM_AUTH_REQUIRED` 设为 `1` 强制校验。

**主题**：顶部太阳/月亮按钮切换深浅色，选择记在浏览器本地，刷新后保持。
管理台 12 个视图与所有图表都跟随主题（图表色走 CSS 变量）。

## 5. 部署流程

### 5.1 后端（改动 Python 代码时）

```bash
cd impl
tar -czf /tmp/pdm.tgz --exclude='.venv' --exclude='__pycache__' \
  services packages tools
scp /tmp/pdm.tgz root@10.167.2.175:/root/
ssh root@10.167.2.175 '
  rm -rf /root/pdm-src && mkdir -p /root/pdm-src
  tar xzf /root/pdm.tgz -C /root/pdm-src && cd /root/pdm-src
  docker build -q -t 10.167.2.175:30500/pdm/python-diagnosis:0.9.5 -f /root/AppGlibc .
  docker push 10.167.2.175:30500/pdm/python-diagnosis:0.9.5
  kubectl -n pdm-prod set image deploy/python-diagnosis api=10.167.2.175:30500/pdm/python-diagnosis:0.9.5
  kubectl -n pdm-prod rollout status deploy/python-diagnosis --timeout=150s
'
```

> ⚠️ **两个高频坑**
> 1. `kubectl set image` 的容器名必须对：python-diagnosis 是 `api`，java-asset 是 `asset`（**不是 `app`**）。写错会静默失败，镜像纹丝不动。
> 2. 节点 CPU 配额紧张，滚动更新时新 Pod 可能 `Pending`。先 `kubectl -n pdm-prod delete pod <旧Pod>` 腾出资源。

### 5.2 前端（改 HTML 时）

```bash
cd impl
bash tools/deploy_dashboard.sh deploy
# 脚本会：上传 3 个页面 → 更新 ConfigMap → 轮询 Pod 内文件同步 → 逐页校验 200
```

ConfigMap 挂载同步最长约 60–90 秒，脚本会轮询等待。

## 7. 排障手册

### 7.1 页面打不开

| 现象 | 排查 | 处置 |
|---|---|---|
| 域名解析失败 | `nslookup pdm-api.10.167.2.175.nip.io` | 内网屏蔽公网 DNS 时改 hosts |
| 401 | 凭据错误 | 用 `pdmadmin` / `3r5P-ygrg-WAcK-W0yB-Vz1q` |
| 503 | Secret 缺失 | `kubectl -n pdm-prod get secret pdm-dashboard-auth` |
| 502/504 | 后端未就绪 | `kubectl -n pdm-prod get pods` |
| 页面空白但 DOM 有内容 | 布局塌陷 | 检查 `<section class="view">` 是否在 `.main` 内 |

### 7.2 某视图空白

打开浏览器控制台，应看到 `[view:xxx]` 错误（路由已加错误边界，
失败时页面会显示「页面渲染失败」+ 错误摘要，不再静默留白）。

### 7.3 接口慢

| 慢的接口 | 原因 | 处置 |
|---|---|---|
| `/v1/stats/system` | `feature_point` 1 亿行 COUNT | 已改为大表估算；若仍慢查 TiDB 统计信息 |
| `/mcp` `list_hot_assets` | 200 台设备算健康度 | 前端已两段式加载；可降 limit |
| `/v1/diagnoses` | 全表扫 | 已加 `ORDER BY created_at DESC LIMIT` |

### 7.4 服务间调用超时（历史坑）

若出现「看板正常、服务间调用超时」，先查 **Egress NetworkPolicy**：

```bash
kubectl -n pdm-prod get netpol allow-egress-backends -o yaml
# egress 里必须有 to: [{podSelector: {}}] 允许同命名空间
```

详见 [33_遗留项清零报告](33_遗留项清零与人工测试就绪报告.md) §2。

### 7.5 告警同步后数量不增

这是**正常行为**——同设备同规则已有未关闭告警时跳过。
若需重新生成，先关闭旧告警：

```bash
curl -X POST http://10.167.2.175:32231/pdm-api/v1/alerts/<id>/ack \
  -H "Host: pdm-api.10.167.2.175.nip.io" -H "X-Tenant-Id: site-a" \
  -H "Content-Type: application/json" \
  -d '{"action":"close","by":"ops"}'
```
