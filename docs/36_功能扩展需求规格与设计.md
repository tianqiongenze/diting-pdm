# 36 · 功能扩展需求规格与设计说明（SRS + SDD）

> 版本 v1.0 · 2026-10-23 · 阶段：需求 → 设计
> 目标：在对标业界 PdM/EAM 标准模块的基础上，补齐本项目缺失的业务闭环页面
> 原则：**每个新页面必须有真实数据支撑，不造假数据、不做纯装饰页**

---

## 一、业界对标调研

### 1.1 调研来源

| 来源 | 关键结论 |
|---|---|
| Siemens Senseye | 强调「holistic asset health visibility」与**优先级排序**；明确指出行业痛点是 *"alerts without clear priorities"*（告警多但无优先级） |
| 工业设备管理平台（CSDN/知乎多篇） | 五大核心模块：**台账、点检、保养、维修、备件** |
| PdM 算法六大模块 | 数据采集 → 特征工程 → 健康评估 → 故障诊断 → 寿命预测 → 决策建议 |
| 设备全生命周期管理 | 台账 → 流转 → 点检 → 保养 → 维修 → 备件 → 报废 |

### 1.2 标准模块清单与本项目覆盖度

| # | 标准模块 | 本项目现状 | 差距 |
|---|---|---|---|

| 5 | 诊断分析 | ✅ 诊断工作台 | 缺历史记录检索 |

### 1.3 本期范围决策

**做（6 个页面）**——均可用现有真实数据支撑：

| 优先级 | 页面 | 数据来源 |
|---|---|---|
| P0 | 告警中心 | `alert` 表（本期实现生成逻辑）+ `read_asset_health` |
| P0 | 设备 360 详情 | `asset` + `component` + `measurement_point` + `diagnosis` + `recommendation_card` |
| P1 | 诊断历史 | `diagnosis`（720 行） |
| P1 | 成本效益分析 | `recommendation_card.economics` + `options.cost` |
| P2 | 组织与产线 | `org_node`（32 节点）+ `asset.node_id` |
| P2 | 系统运维 | `/healthz` `/events/stats` `/integration/stats` `/cache/stats` + 表行数 |

**不做（3 个）**——需新建表与业务流程，超出本期范围，记入后续迭代：

- 点检巡检（需 `inspection_task` / `inspection_record` 表 + 移动端）
- 保养计划（需 `maintenance_plan` 表 + 到期提醒）
- 权限与用户管理（需 `user` / `role` / `permission` 表 + 登录态）

## 二、需求规格

### 2.1 角色定义

| 角色 | 关注点 |
|---|---|
| 设备主管（equipment_manager） | 全厂健康态势、成本、工单闭环率 |
| 维修主管（maintenance_supervisor） | 待办告警、工单确认、人力与窗口 |
| 可靠性工程师（reliability） | 诊断依据、故障模式、趋势劣化 |
| 值班员（operator） | 当前告警、处置动作 |

### 2.2 功能需求

#### FR-01 告警中心（P0）

**用户故事**
> 作为维修主管，我希望看到按严重度排序的待处置告警，并能一键确认/升级，
> 以便在 SLA 内处理最紧急的设备。

**用例**
- UC-01-1 查看告警列表：按状态（待处置/已确认/已升级/已关闭）+ 等级筛选
- UC-01-2 同步告警：把当前 HI 超阈值的设备写入 `alert` 表（幂等，不重复建单）
- UC-01-3 确认告警：填写处置动作，状态转 `ACKED`，记录 `ack_by` / `ack_action`
- UC-01-4 升级告警：状态转 `ESCALATED`，记录 `escalated_at`

**验收标准**
- [ ] 列表按 SLA 剩余时间升序，超时项红色高亮
- [ ] 同步操作幂等：连续执行两次，告警数不翻倍
- [ ] 确认后状态与 `ack_by` 正确落库
- [ ] 同一设备同一规则在 `OPEN` 状态不重复建告警

#### FR-02 设备 360 详情（P0）

**用户故事**
> 作为可靠性工程师，我希望在一个页面看到某台设备的全部信息（台账、测点、健康趋势、历史诊断、关联工单），
> 以便快速判断该设备是否值得深入分析。

**用例**
- UC-02-1 打开详情：从台账/告警/看板任意入口跳转
- UC-02-2 查看测点：列出该设备全部测点（编号/部件/量/方向/采样率）
- UC-02-3 查看健康历史：近 7 天 HI 曲线 + 当前等级
- UC-02-4 查看历史诊断：该设备最近的诊断记录（时间/HI/等级/模型版本）
- UC-02-5 查看关联工单：该设备的方案卡及状态

**验收标准**
- [ ] 页面标题显示设备位号与名称
- [ ] 测点数与 `/api/v1/assets/{id}` 返回的 `measure_point_count` 一致
- [ ] 健康历史曲线与趋势 API 数据一致
- [ ] 无数据区块显示空状态而非空白

#### FR-03 诊断历史（P1）

**用户故事**
> 作为可靠性工程师，我希望检索历史诊断记录，以便复盘某次判断的依据。

**用例**
- UC-03-1 列表分页，按时间倒序
- UC-03-2 按设备位号搜索
- UC-03-3 查看单条诊断的维度分解与模型版本

**验收标准**
- [ ] 列表默认显示最近 50 条
- [ ] 搜索支持位号前缀匹配
- [ ] 点击行展开维度贡献明细

#### FR-04 成本效益分析（P1）

**用户故事**
> 作为设备主管，我希望看到维护决策带来的净收益、避免损失与成本构成，
> 以便向管理层证明投入产出。

**用例**
- UC-04-1 汇总卡片：总避免损失 / 总成本 / 净收益 / ROI
- UC-04-2 成本构成：停机 / 人工 / 备件 三项占比
- UC-04-3 按设备 Top N 净收益排行
- UC-04-4 按方案（option）维度的成本对比

**验收标准**
- [ ] 净收益 = 避免损失 − 总成本（与单卡 `economics` 口径一致）
- [ ] 成本三项之和等于总成本（误差 < 0.01）
- [ ] Top N 排行按净收益降序

#### FR-05 组织与产线（P2）

**用户故事**
> 作为设备主管，我希望按车间/产线/工位层级看到各节点的设备数与健康分布，
> 以便定位问题集中的区域。

**用例**
- UC-05-1 树形展示 `org_node` 层级
- UC-05-2 每个节点显示设备数、红/橙/黄/绿数量
- UC-05-3 点击节点筛选该节点下设备

**验收标准**
- [ ] 树层级与 `parent_id` 关系一致
- [ ] 节点设备数为其子树汇总
- [ ] 无设备节点显示 0 而非隐藏

#### FR-06 系统运维（P2）

**用户故事**
> 作为平台运维，我希望在一个页面看到服务健康、事件总线、集成队列、缓存与数据规模，
> 以便快速定位异常。

**用例**
- UC-06-1 服务健康：healthz / version / 各依赖状态
- UC-06-2 事件总线：transport / emitted / failures / last_error
- UC-06-3 集成队列：outbox 各状态计数
- UC-06-4 数据规模：核心表行数
- UC-06-5 缓存：L1/L2 命中与键数

**验收标准**
- [ ] 所有指标来自真实 API，不硬编码
- [ ] 异常值（failures > 0、last_error 非空）红色高亮
- [ ] 页面可手动刷新

### 2.3 非功能需求

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-01 | 页面加载 | 内网首屏可交互 < 1.5s |
| NFR-02 | 依赖 | 零外部 CDN，全部内联 |
| NFR-03 | 响应式 | 1366 / 1600 / 1920 无横向滚动 |
| NFR-04 | 可访问性 | 语义化标签、对比度 ≥ 4.5:1（正文） |
| NFR-05 | 兼容 | Chrome/Edge 100+ |
| NFR-06 | 安全 | 沿用 Basic Auth，写操作记录 `ack_by` |
| NFR-07 | 幂等 | 告警同步、工单确认可重复调用不产生重复数据 |

### 3.2 API 契约（新增 7 个）

#### `POST /v1/alerts/sync`
从当前健康状态生成告警（幂等）。

```
请求：{"tenant_id":"site-a","threshold_hi":70}
响应：{"created":2,"skipped":6,"total_open":2}
规则：HI < 70 且 level ∈ {red, orange} → 建告警；同 (asset, rule) 已有 OPEN 则跳过
```

#### `GET /v1/alerts`
```
查询：status（OPEN/ACKED/ESCALATED/CLOSED，可逗号分隔）、level、limit
响应：{"count":N,"alerts":[{alert_id,asset_id,level,rule_id,message,
        action_hint,owner_role,sla_hours,status,ack_by,ack_action,
        created_at,age_hours,sla_remaining_hours,overdue}]}
排序：overdue DESC, sla_remaining_hours ASC
```

#### `POST /v1/alerts/{alert_id}/ack`
```
请求：{"action":"ack|escalate|close","by":"user","comment":"..."}
响应：{"alert_id":..,"status":"ACKED|ESCALATED|CLOSED"}
```

#### `GET /v1/diagnoses`
```
查询：asset_id（可选）、limit（默认 50）
响应：{"count":N,"items":[{diag_id,asset_id,hi,level,model_version,
        degraded,contributions,created_at}]}
```

#### `GET /v1/stats/cost`
```
查询：limit（Top N，默认 10）
响应：{"total":{"avoided_loss":..,"total_cost":..,"net_benefit":..,"roi_pct":..},
        "breakdown":{"downtime":..,"labor":..,"spare":..},
        "by_asset":[{asset_id,avoided_loss,total_cost,net_benefit}],
        "by_option":[{option_id,count,total_cost,avg_downtime_hours}]}
```

#### `GET /v1/org/tree`
```
响应：{"nodes":[{node_id,parent_id,node_type,name,depth,
        asset_count,levels:{red,orange,yellow,green,none}}]}
```

#### `GET /v1/stats/system`
```
响应：{"service":{"version":..,"uptime_s":..},
        "tables":[{name,rows}],
        "events":{transport,emitted,failures,last_error},
        "integration":{...}, "cache":{...}}
```

### 3.4 告警规则设计

| rule_id | 条件 | level | owner_role | SLA |
|---|---|---|---|---|
| `HI_CRITICAL` | HI < 40 | red | maintenance_supervisor | 4h |
| `HI_WARNING` | 40 ≤ HI < 70 | orange | maintenance_supervisor | 24h |
| `DEGRADED` | 诊断 `degraded=1` | yellow | reliability | 72h |

> 阈值可通过 `threshold_hi` 参数覆盖，默认 70。

## 六、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `alert` 表空，首次同步可能一次写入大量告警 | 页面卡顿 | 限制单次同步上限 200 条，超出分页 |
| 成本数据仅 4 张卡，报表样本不足 | 图表无说服力 | 页面标注"样本 N 张"，不夸大结论 |
| `org_node` 与 `asset.node_id` 可能不匹配 | 组织树设备数为 0 | 实现时做左连接，未匹配归入"未分配"节点 |
| 新增 6 视图使单文件过大 | 加载变慢 | 控制在 150KB 内；超限则拆静态资源路由 |
