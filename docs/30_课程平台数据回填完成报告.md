## 三、工具与性能

`tools/seed_course_platform.py` + `tools/seed_all.sh` + `tools/seed_progress.py`

| 阶段 | 吞吐 | 说明 |
|---|---|---|
| 逐批 commit | 827 行/s | 每批都是一轮 TiDB 2PC 往返 |
| 大事务缓冲（10 万行/批） | 7,770 行/s | 提升 9.4 倍 |
| 8 分片并行 | ~6,200 行/s（实测稳定值） | 见下 |

**并发没有线性提升**：4 分片 11,389 行/s → 8 分片仅 ~11,500 行/s，
说明 TiDB 写入路径已饱和，加进程无效。最终稳定在 6,200 行/s 左右
（不同时段有波动，与 discussions/records 等 CPU 密集型阶段交替有关）。

内存方面采用流式生成（按 租户→课程→章节 逐级产出），
内存占用与 1 亿总量无关，这是能跑亿级的前提。

## 四、踩过的坑（按发现顺序）

1. **TRUNCATE 被外键挡住** — TiDB 不允许 truncate 被 FK 引用的表。
   只有 `learning_paths` 被 `learning_path_steps` 引用，故单独用 DELETE。
2. **DELETE 大表触发 8175 内存超限** — 改 TRUNCATE + `tidb_mem_quota_query=8GB`。
3. **TiDB FK 同事务不可见** — 批量插入父行后立刻插子行会误报 1452，
   设 `foreign_key_checks=0`（数据一致性由事后全量校验兜底）。
4. **唯一键冲突** — 知识点/资源 code 原为 `KP0001` 在课程内重复，
   改为带章节序号 `KP050001`；手机号随机碰撞改为确定性生成。
5. **各分片 UUID 撞主键** — 8 个进程 RNG 种子相同，产出同一串 UUID。
   改为 `SEED + si * 100003` 按分片偏移。
6. **`( ... &)` 分离进程被回收** — 工具调用结束时子进程一起被杀。
   改用 `run_in_background` 托管 + 脚本内 `wait`。
7. **进度口径算错** — 我第一版监控把 records 当"每课程"、kps 当"每课"计，
   推出 4.8 亿的错数。实际 records 是**每规则**（30×6×16,000）、
   kps/resources 是**每章**（192,000 章 × 240/200）。
