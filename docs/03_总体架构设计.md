## 1. 架构原则（Architecture Principles）

| ID | 原则 | 理由 | 违反示例（反模式） |
|---|---|---|---|
| **P1** | **建议不指令** | 系统不参与安全联锁，不承担控制责任 | Agent 直接向 PLC 写设定值 |
| **P2** | **证据可回放** | 工业场景要"说错了谁负责" | 只输出"置信度 87%"无依据 |
| **P3** | **降级优于崩溃** | 脏数据、断网、掉线是常态 | 一个通道失效导致整条链停摆 |
| **P4** | **协议无关** | 工厂协议碎片化，上层不应感知 | 诊断代码里写 `if protocol == 'modbus'` |
| **P5** | **人机共决** | 关键决策必须留人工确认 | 自动创建工单并派工 |
| **P6** | **单点可替换** | 开源组件生命周期不可控 | 算法与 supOS/TDengine 深度耦合 |
| **P7** | **配置优于编码** | 新设备接入不应发版 | 每接一台设备改代码重新部署 |
| **P8** | **默认最小权限** | 等保三级 + 工控安全 | Agent 拥有全库读写权限 |

### 3.3 关键架构决策（ADR 摘要）

| ADR | 决策 | 备选 | 理由 | 后果 |
|---|---|---|---|---|
| ADR-001 | 自研 Harness，不直接用 LangGraph/CrewAI | LangGraph、CrewAI、Hermes Agent | 工业场景需要"权限+审计+Stop Hook"一等公民；框架抽象会隐藏关键控制点 | 开发量 +15%，可控性 +100% |
| ADR-002 | 时序库选 TDengine | InfluxDB、TimescaleDB | 国产、压缩率高（10:1+）、单机吞吐强、支持降采样 | 生态较弱，需自建运维 |
| ADR-003 | 诊断引擎插件化（策略模式 + 注册表） | 单体 | 模型会换（LimiX 许可风险） | 需定义稳定接口 |
| ADR-004 | 会诊用"并行 fan-out + 独立 Evaluator" | 单一 Agent 串行 | 防自说自话；可解释 | token 成本 ×4（可接受） |
| ADR-005 | 边缘用 K3s，不用 OpenClaw 生产 | OpenClaw | 高频变更不适合产线 | 失去"自主写代码"能力，用配置替代 |
| ADR-006 | 原始波形留厂，只传特征 | 全量上云 | 合规 + 带宽 | 云端无法重算，需边缘可回放 |
| ADR-007 | MCP 作为唯一对外工具协议 | 自定义 REST | 生态兼容、可被任意 LLM 客户端调用 | 需做 MCP 网关鉴权 |
| ADR-008 | 报告用 HTML（非 PDF 优先） | PDF | 可交互（缩放频谱）、可嵌入证据 | 归档需另存 PDF |

> ADR 全文在 Ph1 落地为 `docs/adr/ADR-00x.md`，每条含"背景-决策-后果-状态"。

## 4. 数据架构（TOGAF 阶段 C-数据 / 4A 之 DA）

### 4.1 数据分层

| 层 | 内容 | 存储 | 保留 |
|---|---|---|---|
| ODS 原始层 | 原始报文、原始波形 | 对象存储 + 边缘盘 | 90 天（波形）/ 1 年（报文） |
| DWD 明细层 | 清洗后时序、对齐后多源 | TDengine | 3 年 |
| DWS 汇总层 | 小时/日聚合、特征宽表 | TDengine + PG | 5 年 |
| ADS 应用层 | HI、RUL、告警、方案卡 | PG | 5 年 |
| 知识层 | 故障模式、案例、判据、技能 | PG + 图库 + 向量 | 永久 |

### 4.2 统一命名空间（核心设计）

```
{site}.{area}.{asset}.{component}.{point}.{quantity}
例：SZ01.压缩车间.KA-101.驱动端轴承.DE_H.vibration.acc_rms

规则：
· 全小写，点分隔，6 段固定
· asset 使用位号（与 P&ID 一致）
· point 使用 ISO 13373 方位约定（DE/NDE × H/V/A）
· quantity 使用 UCUM 单位编码
```

**为什么重要：** 这是"协议无关"的落地手段。上层永远只认这个路径，换 PLC 不影响任何上层逻辑。

### 4.3 数据流

```
传感器 ──(4-20mA/IEPE)──► 采集卡 ──(Modbus/OPC UA)──► ingest-gateway
                                                          │
                                    ┌─────────────────────┤
                                    ▼                     ▼
                              原始波形→对象存储     特征值→Kafka→ts-writer→TDengine
                                                          │
                                                          ▼
                                            feature-engine（滑动窗特征）
                                                          │
                                              ┌───────────┴──────────┐
                                              ▼                      ▼
                                     diagnosis-engine         alert-service
                                              │                      │
                                              ▼                      ▼
                                     diagnosis 记录           分级路由/升级
```

### 5.2 部署拓扑（云边协同）

```
┌─────────────────── 厂区（OT 域）───────────────────┐
│                                                    │
│  [PLC/传感器] ──► [工业交换机] ──► [边缘节点 ×N]    │
│                                      │ K3s         │
│                                      │ ingest      │
│                                      │ feature     │
│                                      │ 本地诊断     │
│                                      │ 本地 LLM(可选)│
│                                      │ 缓存 72h     │
└──────────────────────────────────────┼─────────────┘
                                       │ 单向数据闸（OT→IT）
┌──────────────────────────────────────▼─────────────┐
│                   厂区 IT 域 / 私有云               │
│  [API 网关] ─ [agent-runtime] ─ [decision-service]  │
│  [TDengine] [PG] [MinIO] [Kafka] [Neo4j]           │
│  [Grafana] [Loki] [ArgoCD]                         │
└──────────────────────────────────────┬─────────────┘
                                       │（不出厂，仅运维通道）
                                   [运维 VPN]
```

**关键设计：**
- 数据闸**单向**（OT→IT），反向仅允许运维白名单端口。
- 边缘节点**自治**：中心挂了不影响本地诊断与告警。
- 模型更新走"边缘拉取 + 灰度"，不推。

## 7. 架构治理（TOGAF 阶段 G 前置）

| 机制 | 内容 | 频率 |
|---|---|---|
| 架构评审委员会 | 架构师 + 设备专家 + 安全 + 平台负责人 | 每个 Gate |
| ADR 机制 | 每个重大决策一页纸，纳入版本库 | 随时 |
| 技术债登记 | 记录已知妥协与偿还计划 | 每迭代 |
| 合规检查 | 对照 docs/12 标准矩阵逐条核 | 每阶段 |
| 架构契约测试 | 服务间接口契约测试（Pact 类） | 每次 CI |

**架构例外流程：** 任何违反 P1–P8 原则的设计，必须提交"例外申请"，说明理由、风险、补偿措施、失效期，由架构委员会批准。**没有例外流程的原则等于没有原则。**
