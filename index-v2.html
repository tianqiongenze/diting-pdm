02

三个结构性缺陷（不是补丁，是换地基）

A 假设了单厂

真实是 20 基地 + 供应商，跨省跨国、网络参差、要能独立生存。

解法：多租户 + 联邦部署 + 数据主权分级。

B 假设读写同库

真实是高频写 + 跨基地重查询，一套库必然互相拖垮。

解法：CQRS 分离，写侧时序/对象，读侧 PG + TiFlash。

C 假设单一语言

协议解析要 Rust，事件管线要 Go，企业集成要 Java，AI 要 Python。

解法：按部署边界分工，统一门禁。

集群实盘盘点（10.167.2.175 / .176）

不是推测，是 2026-10-21 的实际查询结果。结论直接改写 D14 / D15。

项实盘结果判断
集群K8s v1.28.2，master 16C/126Gi + worker1 64C/126Gi，docker 26.1.4，CentOS 7可用，实际 CPU 仅 2–10%
管理面Rancher + Fleet + Istio（注入关闭）Fleet 正好管 20 基地边缘
事件总线Pulsar 已在跑（2 bookie + ZK）复用 不建 Kafka
分析库TiDB v8.5.8 + TiFlash 已在跑有条件复用 见下
向量 / 图Milvus + NebulaGraph 已在跑复用
LLMLiteLLM + Ollama 已在跑复用
可观测Prometheus + Grafana + Loki 已在跑复用 不自建
时序库无 TDengine / InfluxDB必须新建
关系库PG 15.12 仅存在于 dify-plus（Dify 自用）不建议混用

⚠ TiDB 当前不稳定的证据

  • tikv-2 重启 88 次，tikv-1 重启 34 次
  • Last State: Terminated，Exit Code 137（SIGKILL / 典型 OOM）
  • TiKV 3×10Gi，TiFlash 10Gi，local-path 不支持扩容

结论：可做分析与读模型，不可做生产主库，除非先调资源并扩容。

存储三分法（ADR-017）

  • TDengine：时序特征值（必须新建）
  • PG16：事务域 + 多租户 RLS（新建专用实例）
  • TiDB + TiFlash：跨基地对标读模型（复用）

为什么不全塞 TiDB：无 RLS、容量仅 30Gi、OOM 历史。

05

多语言职责矩阵

语言承担域具体职责选型理由
Rust监测（边缘）协议解析、DSP 核（FFT/包络）、波形编解码无 GC、内存可控、24×7 长稳
Go运营 + 基础设施事件管线、GraphQL BFF、告警路由、审计链、投影器高并发 I/O、单文件部署
Java资产 + 知识 + 集成组织树权限、EAM/ERP 适配、规则引擎、判据库企业中间件生态、Nacos 契合
Python诊断/预后/决策/智能体特征工程、HI/RUL、Harness、MCP、报告AI 生态不可替代

铁律

语言按部署边界划分，不按目录；跨语言一律走 gRPC/Pulsar，禁止 FFI 直连；门禁统一（覆盖率 80%/核心 90%），不允许"Python 严、Rust 松"。
